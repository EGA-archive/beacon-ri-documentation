Beacon Template UI
Configuration
Configuration File

The config.json file is the main configuration file for the Beacon Template UI. It allows deployers to customize the application's appearance, available features, and genomic query settings without modifying the frontend source code.

The configuration also defines deployment-specific information, including the Beacon API endpoint, deployment type, supported genome assemblies, and authentication settings.

Configuration file locations:

Runtime configuration: client/public/config/config.json
Example configuration: client/config/config.example.json
It is recommended to keep config.example.json unchanged and use it as a reference when creating or updating the runtime configuration.

The example file illustrates the configuration structure. The authoritative validation rules and default values are defined in the application's validation schema.

Editing the Configuration File
The Beacon Template UI loads its configuration at runtime from /config/config.json. This allows deployers to update configuration values without rebuilding the frontend application.

The configuration is loaded when the application initializes. Changes to the configuration file are therefore picked up when the application is loaded again, provided the updated file is available at the configured location.

Before modifying the configuration, it is recommended to:

Keep a backup or versioned copy of the configuration file.
Ensure that configured URLs and asset paths are accessible in the deployed environment.
Use the correct JSON structure and data types.
Check that configuration values are compatible with the connected Beacon implementation.
The available properties and their validation requirements are described in the configuration tables below.

Configuration Validation
Before the Beacon Template UI starts, the application loads config.json and validates its contents against a predefined Joi validation schema.

The schema checks configuration structure, data types, required properties, accepted values, and conditional dependencies between configuration fields.

During validation, the application also applies the default values defined by the schema where applicable.

Validation uses strict data types. For example, a Boolean property must contain true or false, rather than the strings "true" or "false".

The initial validation collects all detected schema errors rather than stopping at the first error.

If the configuration is valid, the application initializes its authentication settings, stores the validated configuration, and loads the React application.

If configuration loading, validation, or another startup operation fails, the application does not start normally. The error is logged in the browser console, and the following message is displayed:

The application could not start because its configuration is invalid or could not be loaded.
When troubleshooting a startup error, open the browser's developer console for additional information.

The validation schema verifies configuration consistency. It does not verify that external services are reachable or that every configured feature is supported by the connected Beacon backend.

Core Beacon and Configuration Settings
This section defines the core settings used to connect the Beacon Template UI to a Beacon API and configure genomic query options. These settings specify the deployment type, the API endpoint, supported reference genome assemblies, available variant types, and genomic coordinate conventions.

Some genomic settings are optional and are primarily relevant when genomic queries are supported by the connected Beacon.

Login Settings
This section defines the authentication settings available in the Beacon Template UI. Deployers can enable or disable login and configure authentication through an OpenID Connect (OIDC) provider.

Login is disabled by default. When enabled, the application requires a valid OIDC configuration, including a client identifier, provider authority URL, and redirect URI.

Additional OIDC settings are optional and allow deployers to customize authentication behavior according to their identity provider and deployment requirements.

Config Field	Description	Valid Formatting	Notes
ui.showLogin	Controls whether OIDC-based login functionality is enabled in the Beacon Template UI.	Boolean:
true or false	Optional.

Defaults to false.

When true, a valid ui.auth.oidc configuration is required.

When false, the authentication configuration is optional and may remain in the configuration file.

Only Boolean values are accepted.
ui.auth	Contains the authentication configuration for the application.	Object containing:

oidc	Required when ui.showLogin is true.

Optional when login is disabled.

Authentication settings are configured directly in config.json under this object.
ui.auth.oidc	Contains the settings used to configure the OpenID Connect authentication client.	Object containing OIDC configuration properties.	Required when ui.showLogin is true.

When login is enabled, the following properties must be provided:

clientId
authority
redirectUri

The remaining OIDC settings are optional.
ui.auth.oidc.clientId	Defines the client identifier assigned to the application by the OIDC provider.	Non-empty string.	Required when ui.showLogin is true.

The value must match the client identifier registered with the identity provider.

Example:

"clientId": "your-registered-client-id"

A Client ID identifies an application and is not the same as a Client Secret.
ui.auth.oidc.authority	Defines the authority URL of the OIDC identity provider.	Valid HTTPS URL.	Required when ui.showLogin is true.

The URL must use HTTPS.

Example:

"authority": "https://login.aai.lifescience-ri.eu/oidc"

Deployers can use Life Science Login or another compatible OIDC provider.
ui.auth.oidc.redirectUri	Defines the URL to which the identity provider redirects the browser after authentication.	Valid HTTP or HTTPS URL.	Required when ui.showLogin is true.

The URL must match a redirect URI registered with the identity provider.

HTTP is accepted by the schema for local development. HTTPS should be used in production.

Example:

"redirectUri": "http://localhost:3000"
ui.auth.oidc.autoSignIn	Controls the automatic sign-in setting passed to the OIDC authentication provider.	Boolean:
true or false	Optional.

The validation schema does not assign a default. However, the application defaults this setting to false when it is omitted.

Set to true to enable the OIDC provider's automatic sign-in behavior.

Independently of this setting, visiting the /login page automatically starts the authentication process when the user is not already authenticated.

Example:

"autoSignIn": false
ui.auth.oidc.scope	Defines the OIDC scopes requested during authentication.	Non-empty string containing space-separated scope identifiers.	Optional.

If omitted, the following default is used:

"openid profile email ga4gh_passport_v1 offline_access"

Deployers can customize the requested scopes according to those supported by their identity provider.

The schema validates the value as a non-empty string but does not verify individual scope names.
ui.auth.oidc.automaticSilentRenew	Controls whether the authentication client attempts to renew tokens automatically.	Boolean:
true or false	Optional.

When true, automatic token renewal is enabled through the authentication client.

Successful renewal depends on the authentication provider and the supported renewal mechanism.

The schema does not assign a default value.
ui.auth.oidc.silentRedirectUri	Defines an optional callback URL used for silent authentication renewal.	Valid HTTP or HTTPS URL.	Optional.

This property can be configured when the selected OIDC integration requires a dedicated silent renewal callback.

The URL should be registered with the provider when required by its configuration.

No default is defined by the schema.
ui.auth.oidc.postLogoutRedirectUri	Defines the URL to which users may be redirected after signing out.	Valid HTTP or HTTPS URL.	Optional.

The redirect destination should be compatible with the logout configuration of the identity provider.

Example:

"postLogoutRedirectUri": "https://your-beacon.org/"

No default is defined by the schema.
ui.auth.oidc.loadUserInfo	Controls whether the authentication client requests additional identity information from the provider's UserInfo endpoint.	Boolean:
true or false	Optional.

Availability of additional user information depends on the identity provider, its supported claims, and the requested scopes.

No default is defined by the schema.
ui.auth.oidc.autoSignOut	Controls whether the authentication client automatically redirects users to the identity provider when silent renewal fails.	Boolean:
true or false	Optional.

The schema accepts either Boolean value but does not assign a default.

The resulting behavior depends on the authentication library and provider.
ui.auth.oidc.popupRedirectUri	Defines an optional callback URL for authentication initiated through a popup window.	Valid HTTP or HTTPS URL.	Optional.

This setting is relevant when popup-based authentication is used.

No default is defined by the schema.
ui.auth.oidc.popupWindowTarget	Defines the window target used for popup-based authentication.	Non-empty string.	Optional.

The schema requires a non-empty string when this property is provided, without restricting it to a fixed list of values.

No default is defined by the schema.
ui.auth.oidc.extraQueryParams	Defines additional query parameters supplied to the OIDC authorization endpoint.	Object containing string keys and string values.	Optional.

Property names must be non-empty strings. Every value must be a string.

No default is defined by the schema.
ui.auth.oidc.metadata	Allows additional OIDC provider metadata to be supplied through the configuration.	Object.	Optional.

The schema allows additional properties inside this object without validating their individual structure.

Deployers should ensure that any supplied metadata is compatible with the selected OIDC provider and authentication library.

Note on OIDC Configuration:

The Beacon Template UI uses OIDC configuration properties under ui.auth.oidc.

When login is enabled, deployers must provide a registered Client ID, an HTTPS authority URL, and an HTTP or HTTPS redirect URI.

The OIDC client configuration does not define a Client Secret property. Client Secrets must not be exposed through publicly accessible frontend configuration or browser code.

The validation schema checks configuration formats and required fields. It does not verify that credentials are registered with the provider, that callback URLs are authorized, or that the provider supports every configured option.
Example OIDC Configuration

The following example shows the minimum required authentication properties when login is enabled, along with an optional setting for automatic sign-in.

"showLogin": true,
"auth": {
  "oidc": {
    "clientId": "your-registered-client-id",
    "authority": "https://login.aai.lifescience-ri.eu/oidc",
    "redirectUri": "http://localhost:3000",
    "autoSignIn": false
  }
}
The example represents the contents of the ui object in config.json. For production deployments, use the appropriate registered redirect URI, normally with HTTPS.

Entry Types, Common Filters and Genomic Annotations Settings
This section describes how deployers can configure the preferred order of Beacon entry types and customize the Common Filters and Genomic Annotations sections in the Beacon Template UI.

Entry type identifiers must be compatible with the connected Beacon. Common Filters allow deployers to organize predefined filtering terms into categories, while Genomic Annotations allow configurable genomic query examples to be grouped into categories.

The validation schema defines the accepted formats, maximum numbers of configurable entries, and relationships between these settings.

Config Field	Description	Valid Formatting	Notes
ui.entryTypesOrder	Defines the preferred display order of Beacon entry types in the user interface.	Array of unique, non-empty strings.	Optional.

If omitted, the following preferred order is used:

["g_variants", "individuals", "biosamples", "analyses", "cohorts", "datasets", "runs"]

Deployers can customize the list using entry type identifiers supported by their Beacon implementation.

The schema does not impose a fixed list of identifiers or a maximum number of entries. Duplicate values are not allowed, but an empty array is accepted.

Entry type identifiers are defined by the backend. The schema does not verify them against the Beacon's /map response.

When a recognized genomic variation entry type, such as "g_variants", is configured, ui.genomicQueries becomes required, with at least one genomic query type enabled.
ui.commonFilters	Configures the predefined filtering terms and their categories in the Common Filters section.	Object containing:

filterCategories
filterLabels	Optional.

When this object is provided, both properties are required.

At least one actual filtering term must be configured across all categories.

Filtering term identifiers, types, and scopes should be compatible with the connected Beacon.

OIDC Login Setup
The Beacon Template UI supports authentication through an OpenID Connect (OIDC) identity provider.

Authentication is optional and is controlled by the ui.showLogin property in config.json. When login is disabled, the application starts without initializing the OIDC authentication provider.

When login is enabled, deployers must configure an OIDC client and register the appropriate application URLs with their chosen identity provider.

1. Enable OIDC Authentication
Set ui.showLogin to true and provide the required properties inside ui.auth.oidc.

The following configuration is an excerpt from the ui object, rather than a complete config.json file.

"showLogin": true,
"auth": {
  "oidc": {
    "clientId": "your-registered-client-id",
    "authority": "https://your-oidc-provider.org",
    "redirectUri": "https://your-beacon.org/",
    "autoSignIn": false,
    "automaticSilentRenew": true,
    "scope": "openid profile email"
  }
}
The required OIDC properties are:

clientId: the client identifier registered with the identity provider.
authority: the HTTPS URL of the OIDC provider.
redirectUri: the application's authentication callback URL, which must be registered with the provider.
The remaining properties in this example are optional. Detailed validation rules are available in the Login Settings section.

2. Register the Application with an OIDC Provider
Before enabling authentication, register the Beacon Template UI as an OIDC client with a compatible identity provider.

Life Science Login is one possible provider, but it is not required. Deployers can use another OIDC provider compatible with the authentication library.

During registration, ensure that:

The registered Client ID matches ui.auth.oidc.clientId.
The configured authority points to the correct OIDC provider.
The registered redirect URI matches ui.auth.oidc.redirectUri.
The provider supports the requested authentication scopes.
The provider supports the authorization code response type used by the application.

Note on Client Credentials:

The current OIDC configuration is created using the properties defined in ui.auth.oidc.

The authentication configuration uses a Client ID but does not include a Client Secret.

A Client ID is a public application identifier. Client Secrets must not be placed in publicly accessible frontend configuration files, environment variables embedded into browser bundles, or client-side JavaScript.
3. Authentication Initialization
The application loads and validates the runtime configuration before initializing React.

When ui.showLogin is true, the application creates the OIDC configuration and initializes the authentication provider.

When login is disabled, the application starts without the OIDC authentication provider.

The supported configuration properties are described in the Login Settings section.

The authentication response type is set internally to "code" and cannot be changed through config.json.

The supported OIDC properties defined in the validation schema are forwarded to the authentication provider when login is enabled.

Optional settings include silent token renewal, logout redirects, user information retrieval, popup authentication settings, and provider-specific parameters.

Their availability and behavior depend on the identity provider and authentication library. Configuring popup settings does not automatically enable popup login in the current interface.

The application also defines a callback to redirect users to their previously requested page after successful authentication.

4. Authentication Callback and Redirect
When login is enabled, routes protected by ProtectedRoute require an authenticated user.

If an unauthenticated user requests a protected page, the application saves the original local URL in session storage and redirects the user to /login.

The saved URL includes the pathname, query parameters, and URL fragment, allowing users to return to the exact location they originally requested.

Currently, the Dataset Detailed Table (/dataset-detailed-table) and Allele Frequency (/allele-frequency) pages use ProtectedRoute.

Other main application routes are not protected by this component. Frontend route protection does not replace backend API authorization.

When the identity provider redirects the browser to the application with both code and state query parameters, the application displays a loading indicator while authentication is being processed.

The Login page automatically initiates the OIDC authentication process when the user is not already authenticated.

While the authentication session is being checked or the browser is being redirected to the provider, the following message is displayed:

You will be redirected to the login shortly

No additional login button interaction is required on this page.


Authentication Callback Message:

Completing log in...

You will be redirected to the requested page shortly.
After successful authentication, the application retrieves the saved local return path and redirects the browser to that location.

If no valid local return path is available, the application redirects to the home page at /.

The stored return path is removed after it is read.

5. Validate the Authentication Setup
After updating config.json, reload the application and verify that authentication initializes correctly.

If the required OIDC configuration is missing or invalid, application startup fails and an error is logged in the browser console.

Configuration validation does not verify that the identity provider is reachable or that the registered callback URLs and scopes are accepted by the provider. These should be tested against the configured authentication service.



Single Beacon and Beacon Network: Configuration and UI Differences
The Beacon Template UI supports both Single Beacon and Beacon Network.
The UI has been architected to allow a seamless transition between the two modes. Switching from one type to the other does not require structural UI changes. The behavior automatically adapts based on the chosen configuration.

The differences can be grouped into two macro aspects:

Configuration (setup level)
User interface (visual and interaction level)
From a setup perspective, the difference is minimal. To switch between a Single Beacon and a Beacon Network, deployers only need to:

Set the correct beaconType
Provide the correct apiUrl
Example:

{
  "beaconType": "singleBeacon",
  "apiUrl": "https://your-single-beacon.org/api"
}
or

{
  "beaconType": "networkBeacon",
  "apiUrl": "https://your-beacon-network.org/api"
}
There are no structural changes required in the UI code. The behavior adapts automatically based on the selected beaconType. While the configuration change is small, the user experience changes significantly.
The differences affect:

Beacon Browser (Main Page)
When you access the Beacon Browser, the main page displays key information about the Beacon(s) available to you.

If you are browsing a single Beacon, you will see details specific to that Beacon, such as the organization name and URL, as well as the description of the datasets it contains.
If you are browsing a Beacon Network, the page highlights the participating organizations by displaying their logos. This provides a quick visual overview of which institutions are part of the network.
Comparison of the Single Beacon and Beacon Network home pages
Beacon Network Tab
When accessing a Beacon Network, an additional tab appears in the navigation bar. Selecting this tab opens a dedicated page with detailed information about each Beacon within the network.

Navigation bar comparison between Single Beacon and Beacon Network
Results Table
The most significant changes are reflected in the results table.

In the Single Beacon interface, results are presented in a flat, dataset-centered table.
In the Beacon Network interface, results are displayed in a hierarchical, expandable table. The table first presents summary information at the Beacon level (such as maturity level and number of datasets). Users can then expand each Beacon to view detailed information about the datasets it contains. This structure provides a clearer overview at the network level while maintaining access to dataset-level detail when needed.
